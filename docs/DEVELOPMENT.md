# WinTabDock 開発メモ

使い方は [README](../README.md)。ここには、仕組みと、変えるときに守ること・試して分かったこと。

## ソースから動かす・exe を作る

```sh
uv run wintabdock.py              # wintabdock.toml のツールを並べたドックを開く (wintabdock.example.toml を写して作る)
uv run wintabdock.py --rescue     # ドックが落ちて隠れたままの窓を元に戻す
pwsh packaging/build.ps1        # dist/WinTabDock/ に WinTabDock.exe (窓なし) と _internal/ を作る (exe の隣の wintabdock.toml は残す)
pwsh packaging/build.ps1 -Zip   # 配布用の dist/WinTabDock-<版>-win-x64.zip も作る (設定は見本を入れる)
uv run demo/shoot.py            # README の画面 (架空のデモアプリを取り込んだドック) を撮り直す
```

- 設定は exe の隣の `wintabdock.toml`。ビルド時に無ければ見本を置く (あれば上書きしない)
- 「設定」の「ログイン時に起動する」で、HKCU の Run に exe の場所を登録する。exe を移動したら入れ直す
- 窓なしの exe では `sys.stdout` が `None`。`sys.stdout.reconfigure()` をそのまま呼ぶと起動しなかった
- アイコンの元は `assets/icon.svg` (48px 以上) と `assets/icon-small.svg` (32px 以下)。`uv run tools/make-icon.py` で ICO を作り直す
- exe の確かめ方: `uv run check_exe.py`。exe を一時フォルダにコピーし、PortWho と RepoTether だけの設定と
  `WINTABDOCK_HOME` (控えと前回のタブの置き場所) を一時フォルダに向けて動かす。人の前回のタブや他のツールには触れない

## 仕組み (仮想タブ)

相手の窓の中に手を入れず、トップレベルの窓のまま扱う。

- 取り込むと、タイトルバーと縁を外し、**窓の所有者 (owner) をドックにして**本体の上に重ねる
  (`SetWindowLongPtr(GWLP_HWNDPARENT)`)。所有される窓は Windows が常に所有者より手前に置き、最小化も一緒になり、
  タスクバーのボタンも出ない。念のため `WS_EX_TOOLWINDOW` も付ける
- 所有者を付け替えた直後や隠していた窓を出した直後は、重なり順がまだ組み直されていない。ドックを一度 `HWND_TOP` に動かす
- 選んでいないタブの窓は隠す。ドックの移動・大きさ変更に合わせて、選んでいる窓を動かす (重なり順には触らない)
- 取り込んだ窓はタイトルバーを外して隠すので、窓を探しても見つからない。二重起動を避けるため、タブに exe を覚えておく
- 元に戻すときは、属性を戻して見せたあと `ITaskbarList::AddTab` でタスクバーのボタンを明示的に足す。属性が元どおりでも
  タスクバーがボタンを付け直さないことがあった (自動で取り込んだ PortWho が、ドックを閉じたあとタスクバーに出なかった)
- 取り込んだ窓の元の状態 (枠・所有者・位置) は `%LOCALAPPDATA%\WinTabDock\state-<プロセス番号>.json` に控える。
  ドックが落ちても相手の窓とプロセスは残り (所有者が外れるだけ)、次の起動か `--rescue` で元の枠に戻る。
  戻すのは、もう動いていないドックの控えだけ。1 つの `state.json` を共有していたときは、2 つ目のドックが
  動いている方のドックの控えを「前回落ちたもの」と取り違えて窓を戻し、控えを消した。
  以前の共有の `state.json` は、ほかにドックが開いていないときの `--rescue` でだけ扱う

### 採らなかったやり方 (試して問題が出たもの)

最初は所有者を変えず、前面の窓の変化を見張って重なり順を自分で直していた。次の問題が順に出て、所有者方式に切り替えた。

- 別プロセスの窓は `HWND_TOP` で上げても前面の窓より上に上がらず、ドックのタイトルバーで戻るとツールが他のアプリの後ろに残った
- `SetForegroundWindow` でツールを前面にすると、枠やタイトルバーを押した瞬間に前面が移ってリサイズ・移動が取り消された
- ボタンを離すまで待つと、押している間 (移動・リサイズ・「+ 起動」) は本体が真っ暗に見えた
- 前面の変化 (WinEvent) を tkinter の mainloop と同じスレッドで受けると、Python ごと落ちた
  (`PyEval_RestoreThread: the GIL is released`)。別スレッドで受ける必要があった
- 所有者を変えると、ドックが落ちたときに相手の窓まで壊れる、と心配していたが、実験では窓もプロセスも残った
  (`experiments/owner_probe.py`)

## 確かめ方 (自分のツール PortWho・RepoTether などを使う。対象のツールとほかのドックを閉じてから流す)

```sh
uv run wintabdock.py --selftest LPortMan PortWho   # 取り込み・二重起動・切り替え・リサイズ・移動 (途中も見えるか)・メニュー・最小化・別アプリとの重なり・起動時に開く・閉じるときのツール・外す・閉じる・自動取り込み (48 項目)
uv run check_rescue.py LPortMan                  # 取り込んだまま落として、--rescue で戻るか
uv run check_state_files.py                      # 動いているドックの控えに触らないか (窓には触れない)
uv run check_session.py PortWho RepoTether       # 前回のタブ: 起動中なら取り込み、なければ起動して並べ直すか
uv run check_startup.py PortWho RepoTether       # 起動時に開く: 選び方ごとに開くもの・起動するものが変わるか
uv run check_taskbar.py PortWho RepoTether       # ドックを閉じたあと、ツールがタスクバーに戻るか (UI Automation で見る)
uv run check_close.py PortWho RepoTether         # × を押したとき: 一緒に閉じる / 残す / たずねる / × を無視するアプリ
```

- 試験で起動する補助のアプリは、出力を引き継がせない (`stdout=DEVNULL`)。引き継ぐと、補助のアプリが試験の出力の
  パイプを持ち続け、試験を指揮するスクリプトが出力の終わりを待って止まった

- タスクバーに出るかは、窓の属性 (所有者・拡張スタイル) では分からない。属性は元どおりでもボタンが無いことがあった。
  タスクバーのボタン名を UI Automation で読んで確かめる

- 試験のドックが扱うのは、試験の対象に挙げたツールだけ (自動取り込みで、人が使っている他のツールを取り込まないように)。
  前回のタブも人のもの (`session.json`) とは別の `session-selftest.json` を使う
- 前回のタブの試験は、空のタブを復元しても「開き直したタブ = 覚えたタブ」で通ってしまった。期待する並びを試験の側で持つ

- **試験は、対象のツールとほかのドックを閉じてから流す。** 試験の「起動」は起動中の窓を取り込み、最後に閉じるので、
  人が使っているツールを閉じてしまう (RepoTether と PortWho を閉じてしまった)。今は始める前に確かめて止まる

- 位置と表示状態だけ見ると、窓がドックの後ろに回っていても通ってしまう。`WindowFromPoint` が
  その窓を返すか (手前に見えているか) まで見ること
- タブの切り替え・別のアプリから戻る操作・枠のドラッグは、本物のマウスで行う (試験中はカーソルが動く)。
  プログラムから前面化すると、Windows の扱いが人の操作と違い、実際には起きない失敗や、実際に起きる失敗の見逃しになる

## 遠隔で使う (スマホのブラウザから。remote.py)

スマホのブラウザ (noVNC) から WinTabDock につなぎ、スマホの画面の大きさにドックを合わせて使う。
「設定」の「スマホから使う」で入り切りする (入れたかは settings.json の `remote` に覚え、次の起動でも始める)。

```sh
uv run check_remote.py           # ドックに試験用の窓を 3 つ取り込み、noVNC と同じ WebSocket でつなぐ。設定の画面と QR コード、つないでいる間の知らせの窓、表示倍率、絵文字・日本語の変換・カタカナ (Tk と、Tk でない EDIT の窓)、ツールが開くメニューと小窓、つないでいる間に開いた外のアプリの窓も (59 項目。人の WinTabDock が Wi-Fi で待ち受けていると 55)
uv run check_remote_android.py   # Android の実機 (USB デバッグ) の Chrome から。メニューと小窓、iPad の日本語の入力の並び、キーの記録も (19 項目)
uv run check_remote_android.py --lan 192.168.x.x   # スマホは家の Wi-Fi で PC のこのアドレスにつなぐ (USB は試験の操作だけ。20 項目)
```

- **Wi-Fi でつなぐときは、Windows のファイアウォールで受信の許可が要る。** 初めて待ち受けるときに出る確認で許可を押さないと、
  Windows がその Python (exe) の受信を**ブロックする決まり**を自分で作り、以後は確認も出ない。ブロックは許可より強いので、
  許可を足すだけでは通らない。スマホのブラウザは「接続しています」や接続できないページのままになり、remote.log には
  「待ち受けを始めた」しか残らない。管理者の PowerShell で、その exe のブロックの決まりを消し、ポート 15900・プライベートだけの
  許可を足す (2026-10-27 は試験に使う uv の Python 3.13 で、ユーザーがこの手順で通した。配る exe は exe ごとに要る):
  ```powershell
  Get-NetFirewallApplicationFilter | Where-Object { $_.Program -like "*<exe の名前>" } | Get-NetFirewallRule |
    Where-Object { $_.Action -eq "Block" } | Remove-NetFirewallRule
  New-NetFirewallRule -DisplayName "WinTabDock remote" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 15900 -Profile Private -Program "<exe の道>"
  ```
- 家の Wi-Fi は暗号化されていない HTTP なので、同じ Wi-Fi の人には合言葉ごと見えうる。外から使うなら Tailscale (未確認)

- `remote.py` は標準ライブラリだけで書く (exe に Pillow を入れていないので)。撮るのは `PrintWindow`、重ねて縮めるのは GDI の
  `StretchBlt`、送るのは変わった行の帯を zlib で縮めたもの (VNC の Zlib 符号。noVNC が読める)
- 見せるのはドックの内側と、選んでいるツール (と、そのツールが持ち主のダイアログ)。ドック側は `RemoteSource` が窓の並びを渡す。
  遠隔のスレッドから Tk に触らない (Tk の仕事は `call_in_tk` で Tk のスレッドに頼む)
- つないでいる間はドックを画面の右の外に置く (下の「押す (Tk)」の重なりの件)。切れたら元の大きさ・位置に戻す。
  前回の位置 (session.json) には元の位置を覚えるので、つないだまま落ちても次は画面の上に開く
- つないでいる間は、PC の画面の右下に知らせの窓 (`show_remote_notice`。最前面・タスクバーに出さない・閉じられない) を出す。
  ドックが急に消えたように見え、PC の側から取り戻す手段も無かったため。「PC で使う」は待ち受けごと止める
  (接続を切るだけだと、noVNC が `reconnect=true` ですぐにつなぎ直してきて、ドックがまた画面の外に出る)
- **`call_in_tk` で頼んだ処理が例外を出すと、以後の頼み事がすべて届かなくなっていた。** `_drain_tk_calls` が次の予約
  (`after`) をせずに抜けていた。待ち受けに失敗したときの知らせが NameError (`except ... as e` の `e` を後で動く lambda から
  読んだ) を出し、そこで試験ごと止まって見つかった。例外は記録 (remote.log) に書いて続ける
- 試験 (`check_remote.py`) の Wi-Fi の項目は、人が使っている WinTabDock がそのアドレスのポートで待ち受けていたら飛ばす
  (ぶつかって待ち受けられず、試験が落ちた)
- 入れるのは、URL の合言葉 (`?token=`。settings.json の `remote_token`) が合い、`Origin` が `http://<Host>` の WebSocket だけ。
  トップのページ (/) は見せない。配るファイルの道は英数字と `. _ - /` だけ (`..` も断る)。ファイルに触れる前に確かめないと、
  `\\相手\共有` の道で相手の PC へつなぎに行き、サインインの資格情報 (NTLM) を渡しうる。
  「合言葉を作り直す」で前の URL を使えなくする。noVNC は初回に GitHub から取る (版とハッシュを固定)
- 待ち受けるアドレスは、wintabdock.toml の `[remote] host` > 「スマホから使う: アドレスと状態...」の画面で選んだネットワーク
  (settings.json の `remote_network`) > Tailscale > 127.0.0.1 の順 (`Dock.remote_host`)。ネットワークは `GetAdaptersAddresses` で
  表示名 (Wi-Fi など) ごとに並べ、**アドレスでなく名前で覚える** (ルーターがアドレスを変えても選び直さなくてよい)。
  選び直すと待ち受けをやり直す (つないでいるスマホは切れて、noVNC が自分でつなぎ直す)。画面は 1 秒ごとに状態・相手を出し直す。
  URL の合言葉は画面では伏せる (コピーは合言葉入り)
- 画面の右に URL の QR コードを出す (127.0.0.1 で待ち受けているときは出さない)。作るのは同梱の `qrcodegen.py`
  (Project Nayuki 1.8.0、MIT。PyPI の wheel から取り出したそのまま。SHA256 `b089855c...dcc84`)。exe に Pillow を入れていない
  ので、`tk.PhotoImage` に 1 マス 1 画素で描いて `zoom` で広げる。画面に映すものなので誤り訂正は LOW にしてマスを粗くした。
  試験は画面を撮って zxing-cpp で読み、合言葉入りの URL と一致するかを見る (本物のスマホのカメラでは読ませていない)
- ドックで遠隔から押せるのはタブだけ。「+ 起動」「設定」やタブの右クリックはメニューを出し、メニューは別の窓なので遠隔からは見えず、
  開いている間ドックが止まる。押すのを断ったら、離すまで何も送らない (押した状態の移動を送るだけでも、Tk は押されたことにして
  「+ 起動」のメニューが開いた)
- 記録は `%LOCALAPPDATA%\WinTabDock\remote.log`

### ドックに組み込んで分かったこと

- **Tk の時計が止まる。** つないでいる間、Tk のスレッドが `GetMessage` で眠ったまま、`after` の時計の知らせも、別のスレッドからの
  tkinter の呼び出しも来なくなることがあった (数秒〜18 秒。試験の 3 回に 1 回ほど)。Windows の知らせ (`WM_NULL` の Send) には
  すぐ応え、ツールの窓も応えていた。py-spy で見ると Tk のスレッドは `Tcl_WaitForEvent` の `GetMessageW` の中。ドックの窓に
  知らせを 1 つ置く (`PostMessage`) と動き出した。原因は確かめきれていない (`AttachThreadInput` と、ドックが持ち主のツールの窓が
  絡むと見ている)。`call_in_tk` は頼むたびに知らせを置き、つないでいる間は 50ms ごとに置き続ける。置いてからは 13 回続けて出ていない。
  **切ったあとにも起きた。** 頼み事は 20ms ごとの時計 (`after`) で動くので、1 回起こしても時計の前にまた眠り、試験の最後の
  `quit` が届かずドックが閉じなかった (Wi-Fi の試験、2026-10-27。ドックの窓に `WM_NULL` を置いたら閉じた)。
  `call_in_tk` は、頼み事が動くまで 50ms ごとに起こし続ける (`wait=False` でも別のスレッドで起こし続ける)
- **ドックの大きさを変えた直後は、中身がまだ古い大きさ。** `update_idletasks` だけで並べると、ツールを前の幅のまま置き、遠隔の側が
  「ツールが収まらない」と取り違えてドックを縦に伸ばした。`update` で大きさの変化の知らせを処理してから並べる
- **画面の外で出した Tk の窓は、`PW_RENDERFULLCONTENT` で撮ると真っ黒や一部だけ黒い** (つないでいる間にタブを切り替えた窓)。
  窓に描かせる普通の撮り方なら写る。Chromium の窓 (窓の種類の名前が `Chrome_` で始まる窓を含むもの) にだけ
  `PW_RENDERFULLCONTENT` を使い、真っ黒ならもう一方で撮り直す。黒の判定は色の 3 バイトだけで見る (4 バイト目は 0 とは限らない)
- 切り替えたツールに合わせて大きさを合わせ直す (最小の幅のあるツールなら、縮めて縦に伸ばす)
- **表示倍率** (`View.zoom`、settings.json の `remote_zoom`、50〜150% の 7 段): ドックを「頼まれた大きさ ÷ 倍率」で作り、倍率を掛けて
  見せる (`_fit` は `min(倍率, 幅の比, 高さの比)`)。タップの座標は同じ倍率で戻すので、そのまま合う。変えるボタンは、つないでいる間だけ
  帯の「+ 起動」「設定」(どのみち遠隔からは押せない) の代わりに出し、`click_allowed` で遠隔から押してよいものに足した
- **画面より高いドック**: Tk の `wm maxsize` の既定は画面の大きさで、Windows がそこで止める (1080 の画面で内側 1061)。
  つないでいる間だけ `maxsize(8000, 8000)` にし、切ったら戻す。最小の幅のツールも、前は 616x1025 で止まっていたのが縦を使い切る
- **画面の外で広げた所は、描かれるまで 0.5〜1 秒ほど黒い。** 帯も、前の倍率のボタンの絵がしばらく残った。実験では、画面の上なら
  すぐ (5/5)、画面の外では 0.5 秒後は 0/5、1 秒後には描けていた。撮り方 (PW_CLIENTONLY・PW_RENDERFULLCONTENT・窓の DC からの
  BitBlt) を変えても同じで、`RedrawWindow` や Tk の描き直しでも早まらなかった。変わった所は続けて送るので、スマホには 1 秒ほどで
  正しい絵が届く。試験は決め打ちで待たず、正しく写るまで (四隅・ツールの地が白い・帯に前のボタンが無い) 待つ
- **試験の後片付けは、ツールの窓を閉じてからドックを閉じる。** 試験はドックを同じプロセスで開き、別のスレッドで進める。
  先にドックを閉じると mainloop が終わってプロセスが終わり、後片付けのスレッドも止まる。試験用の窓が 90 個残り、
  ドックから戻された窓が人の画面に出たままになった。閉じきれないものは起動役ごと止める (`taskkill /T`)
- 切り替えた直後 (0.2 秒以内) のタップは、30 回に 1 回ほど抜けた (1 秒待てば 30 回とも通った)。未対応

### 試作 (experiments/vnc_probe.py、2026-10-26)

ドックに入れる前に、1 つの窓を VNC で見せて確かめたもの。

```sh
uv run experiments/vnc_probe.py --title PortWho --offscreen   # http://127.0.0.1:15900/ を開く (noVNC が出る)
uv run experiments/vnc_probe.py --exe C:/Tools/x.exe --offscreen --host <Tailscale のアドレス>
uv run experiments/vnc_probe_check.py                         # 試験用の窓 (vnc_testapp.py) で 29 項目
uv run experiments/vnc_android_check.py                       # Android の実機 (USB デバッグ) の Chrome から 8 項目
```

- ポート 15900 (LPortMan の台帳に登録)。同じポートで、ブラウザ (WebSocket) と VNC アプリ (TCP のまま) の両方を受ける。
  最初の 0.4 秒に `GET` が来ればブラウザ、何も来なければ VNC アプリ (VNC はサーバが先に挨拶する)
- ブラウザの側は noVNC 1.6.0。初回に GitHub から取ってハッシュを確かめ、`%LOCALAPPDATA%\WinTabDock\novnc-1.6.0\` に置く。
  `resize=remote` で、ブラウザの大きさ (CSS の px) を SetDesktopSize で送ってくる。スマホなら 412x900 前後になるので、
  文字が豆粒になる心配は小さい。noVNC は、サーバから ExtendedDesktopSize を一度受けるまで大きさを送ってこない
- 画像は Tight の JPEG で送る (変わった範囲だけ)。1 枚撮って送るのに 60〜100ms
- 認証は無い。インターネットに開けない (Tailscale の中だけで使う)
- WebSocket は、`Origin` が `http://<Host>` で、`Host` が待ち受けのアドレスか 127.0.0.1・localhost のときだけ受ける。
  確かめないと、ブラウザで開いているだけのよそのサイトのページが 127.0.0.1:15900 につないで窓を操作できる
  (DNS を書き換えて別の名前で来る手口も Host で断る)。VNC アプリの TCP の接続はブラウザからは作れない

### Android の実機での試験 (2026-10-27、moto g05 / Android 15 / Chrome 155)

- `adb reverse tcp:15900` でスマホの 127.0.0.1:15900 を PC に届ける (Tailscale もポートを開けることも要らない)。
  スマホの Chrome の開発用の口を `adb forward tcp:29222 localabstract:chrome_devtools_remote` で PC に出し、
  本物のタッチ (`Input.dispatchTouchEvent`) と、日本語の確定文字 (`Input.insertText`) を noVNC の入力欄に送る
- 試験は画面の向きを横にして戻す (回転の設定を控えて最後に戻す)。開いたタブも閉じる。ポート 29222 は LPortMan の台帳に登録
- 縦向きはブラウザの中が 411x772 (devicePixelRatio 1.75)、横向きは 828x315。どちらも窓がその大きさになり、
  タップ・長押し・「abc日本語」の入力が通った
- **noVNC が同じ大きさを 1 秒に 10 回頼み続けた。** 幅が 411.43 のように端数になる画面で、受け付けたと返すたびに noVNC が
  表示を作り直し、その拍子に大きさの監視が反応してまた頼んでくる。今と同じ大きさの頼みには「変えない」(状態 1) と返して止めた。
  この間は最初のタップが時々抜けていたが、止めてからは 3 回続けて全部通った
- **絵文字 (🍦 U+1F366) を打つと接続が切れた** (ユーザーの報告、2026-10-27)。noVNC はスマホの絵文字を、1 つの keysym ではなく
  代理対の片方ずつ (0x0100D83C, 0x0100DF66) 2 回に分けて送ってくる。片方だけの文字を `encode("utf-16-le")` して例外になり、
  受け取りのスレッドごと落ちていた (記録にも残らなかった)。前半を控えて後半で 1 文字にする。押す・打つで例外が出ても接続は
  切らず、remote.log に書く。実機で直す前は切れ (11/14)、直した後は打てた
- **Mery に日本語を打てなかった** (ユーザーの報告、2026-10-27)。スマホの日本語の入力 (Gboard) を noVNC は、変換中の文字を
  1 文字ずつ送り、確定すると BackSpace でそれを消してから確定の文字を送ってくる (「に ほ ん ご」→ BackSpace×4 →「日 本 語」。
  実機の Chrome の `Input.imeSetComposition` で再現し、届いたキーを記録して確かめた)。打つものを相手の受け取りの列に置いて
  (PostMessage) いたので順番が崩れた。BackSpace の WM_KEYDOWN は、相手が受け取って翻訳した時に WM_CHAR(8) が列の後ろに作られ、
  先に置いた「日 本 語」に追い越される。Mery は WM_CHAR(8) で消すので「にほ」などが残り、Tk は WM_KEYDOWN の時に列から次の
  WM_CHAR を拾って組にするので「日」を BackSpace と一緒に消した。直し方と、試して駄目だったもの:
  - **1 つずつ渡して処理し終えるのを待つ (SendMessageTimeout) にした。** 翻訳を通らないので、文字を生むキー (BackSpace・Tab・
    Enter・Esc) は WM_CHAR も自分で渡す。Tk には渡さない (Tk は WM_KEYDOWN だけで動く。WM_CHAR(8) を単独で渡しても消えない)。
    BMP の外の文字は、Tk には `WM_UNICHAR` で 1 文字まるごと渡す (代理対を 2 つ渡すとつなげそこねた)。ほかには WM_CHAR 2 つ
  - 渡すのを待つ長さは 5 秒 (`SEND_TIMEOUT_MS`)。500ms では、Tk が絵文字を最初に描くとき (約 1 秒止まる) や縮めた直後に
    時間切れ (1460) になり、その文字や「押した」が捨てられた (後からも処理されない)
  - 駄目だったもの: WM_CHAR(8) だけで送る (Tk で消えない)。文字を `VK_PACKET` の WM_KEYDOWN で置く (別の文字になった)。
    BackSpace を置いた後に WM_NULL を 2 往復して待つ (相手は送られた知らせを先に処理するので、待ちきれないことがあった)
  - 試験は、Tk の窓に加え、Tk でない窓 (experiments/edit_testapp.py。Windows の EDIT 部品だけ。中の文字を WM_GETTEXT で
    読める) に同じ並びで打つ。前の作りではどちらも落ち、今の作りでは通る。実機の Mery でも「abc日本語🍦」になった。
    Mery で Enter・Tab・BackSpace・←・Delete が 1 回ずつ効くことも確かめた
  - 試験の速さでは、「abc」の直後 (0 秒) に変換を始めると、noVNC 自身が最初の「に」を 2 回送ってきた (人の手では間があく)。
    スマホの試験は 0.5 秒あける
- **カタカナに変換すると消えた** (ユーザーの報告、2026-10-28)。noVNC は打った字を `keysyms.lookup` で keysym にするが、その表
  (core/input/keysymdef.js) にある字は Unicode の keysym (0x01000000 + 番号) でなく X の古い keysym で送ってくる。カタカナ
  (ニ = 0x04C6。濁点つきの「ガ」などは表に無く Unicode のまま)・「。」「、」「ー」「「」」・ギリシャ文字・キリル文字など 659 字。
  受け側が Unicode の keysym しか字に戻さず捨てていたので、BackSpace で消した変換中のひらがなの代わりが届かなかった。漢字と
  ひらがなは表に無いので出なかった。表を逆向きにした `keysyms.py` (noVNC の版を上げたら作り直す) で字に戻す。実機で直す前は
  BackSpace×3 の後に 0x4c6 0x4ce 0x4dd 0x4b0 0x4a1 が届いて消え (13/14)、直した後は「ニホンー。」になった
- **Mery のファイルメニューが、スマホではなく PC の画面に開いた** (ユーザーの報告、2026-10-28)。Mery のメニューの帯は窓の中の
  TToolBar で、押すと TrackPopupMenu で Windows 標準のメニュー (#32768 の窓) を出す。メニューはツールの窓とは別の窓で持ち主も
  無いので、写す窓に入っていなかった。さらにドックが画面の外にあるので、Windows はメニューを画面の右端へ寄せて出す (縦の位置は
  頼んだまま)。直し方 (`remote.Menus`):
  - 選んでいるツールと同じスレッドの、見えている #32768 の窓を探し、ドックの横 (画面の外) へ移して重ねる。縦は Windows が
    出した位置 (画面の下で寄せられていたら押した所)、横は押した所。下の段は上の段の右 (入らなければ左)。移した後も
    PrintWindow で撮れ、項目の位置 (GetMenuItemRect・MenuItemFromPoint) も移した先で合う
  - ツールはメニューの処理の中で本物のマウスを見るので、窓へのマウスのメッセージは効かない。メニューの窓に、Windows 自身が
    使うメッセージ (文書には無い) を項目の番号で渡す: MN_SELECTITEM (選ぶ)・MN_BUTTONDOWN (押す。下の段を開く)・
    MN_BUTTONUP (離す。項目を実行)。外を押したら MN_CANCELMENUS で全部閉じ、その押し込みはツールに渡さない
  - キーは受け取りの列から読むので、一番上の段の窓に PostMessage する (下の段の窓に置いても効かなかった)
  - 押した時にメニューを出すツールは、メニューを閉じるまで「押した」の処理から戻らない。待ち続けると受け取りが 5 秒止まるので、

  - メニューは押したまま開くと、「離した」が受け取りの列に来るまで待っていて、キー (↓ Enter) を受け付けなかった。開いた押し込みを

  - 試験は experiments/edit_testapp.py の上の帯 (Mery と同じく押した時に TrackPopupMenu)。直す前はメニューが PC の画面

    Mery そのものでは試していない

### 試して分かったこと

- **撮る**: `PrintWindow(PW_CLIENTONLY | PW_RENDERFULLCONTENT)` で、隠した窓・画面の外の窓・ほかの窓の後ろの窓も撮れた (Tk)
- **大きさ**: 枠のある窓は、Windows が画面の高さより大きくしない (1080 の画面で内側 1061 まで)。
  PortWho は幅 680、LPortMan は 760 より狭くならない。届かなかったときは、画像を縮めて要求された大きさに収め、
  縮めた分だけ窓を縦に伸ばす。クリックの座標も同じ倍率で戻す。PortWho を幅 412 に収めると文字は約 0.6 倍
- **押す (Tk)**: 窓へのメッセージ (`WM_LBUTTONDOWN`) だけでは押されない。Tk は押したかをマウスの状態 (`GetKeyState`) で見る。
  `AttachThreadInput` で相手と入力の状態を共有し、`SetKeyboardState` でボタンを押した状態にしてから
  `SendMessageTimeout` で送る (相手が処理し終わるまで待つ。投げっぱなしだと、状態を戻すのが先になりうる)
- **押す (Tk)**: 押したまま 0.3 秒待つと押されなかった (スマホのタップは 0.1 秒ほど押している)。Tk は本物のマウスカーソルの
  位置を定期的に見に行き、そこに自分が無いと「出た」ことにする。押している間は 20ms ごとに同じ位置への移動を送り続ける。
  試験が時々落ちた (25 項目中 4 つ) のもこれだった
- **押す (Tk)**: 押した所の画面に**別の窓が重なっていると押されない** (最前面の窓で再現)。画面の外に置けば重なりが無く、
  押せる。`--offscreen` はつないでいる間、窓を画面の右の外に置き、終わるときに戻す
- **打つ (Tk)**: Tk は、自分の窓が前面でないと文字を捨てる。押すたびに `WM_ACTIVATE` と `WM_SETFOCUS` を送ると受け付ける
  (本物の前面・フォーカスは動かさない)。文字は `WM_CHAR` で送る。noVNC はスマホの日本語の確定文字を Unicode の keysym
  (`0x01000000 | 文字コード`) で送ってくるので、そのまま `WM_CHAR` にできる (日本語の「あ」で確かめた。スマホの実機は未確認)
- **修飾キー** (Ctrl・Shift・Alt) は窓へのメッセージでは効かない (相手は本物のキーボードの状態を読む)。未対応
- **Chromium (Edge のアプリ窓で確かめた。WebView2 の RepoTether は未確認)**: 画面の上なら、押す・打つ・大きさの変更が効いた。
  画面の外では描くのを止め、灰色が写り、ページの大きさも変わらなかった。起動時に
  `--disable-features=CalculateNativeWinOcclusion --disable-backgrounding-occluded-windows` を付けると、画面の外でも効いた。
  WebView2 なら環境変数 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` で渡せるはず (未確認)
- `--input sendinput` (本物の入力) は書いただけで試していない。手元のマウスを動かし、画面の上の窓にしか届かない
- 画面ロック中に撮れるか・押せるかは試していない (無人の PC をロックすると、試験の後で戻せない)

### 試験で踏んだこと

- 試験用の窓をタイトルの頭 (`vnc-testapp`) だけで探したら、noVNC を開いたブラウザの窓 (題がタイトルを写す) をつかみ、
  ブラウザに文字を打ち込んだ。窓の種類 (`TkTopLevel`) と、起動ごとの目印をタイトルに入れて探す
- noVNC のタブを開いたまま試験を流すと、自動でつなぎ直してブラウザの大きさを要求し、試験の窓の大きさを変えた。先に閉じる
- uv の .venv の `python.exe` は起動役で、窓を持つのは別のプロセス。PortWho (PyInstaller の 1 ファイルの exe) も子プロセスが窓を持つ。
  起動したプロセスの番号では窓を探せない。exe のパスかタイトルで探す
- LPortMan (`lportmanw.exe`) は、stdout に DEVNULL を渡して起動すると、窓を出さずにすぐ終わった。`--exe` では出力をつながない
- 出し直した (`ShowWindow`) 直後の Tk の窓は、子窓がまだ隠れていて、押した先が外れる。少し待つ
